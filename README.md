# Nginx-X

一个基于 Bash 的 Nginx 自动化管理交互脚本（Ubuntu / Debian / CentOS / Alpine / OpenWrt）。

## HTTP/2 配置兼容

HTTPS 新建和保留式转换共用实际 Nginx 版本检测（`NGINX_BIN` 可指定二进制，默认 PATH 中的 `nginx -v`）：官方 **1.25.1 起**使用 TLS server 内的 `http2 on;`，IPv4/IPv6 `listen` 只保留 `ssl`；旧版（包括 1.18/1.22）仍使用 `listen ... ssl http2;`，不会删除或禁用 HTTP/2。版本未知、异常或命令失败时记录提示并保守使用旧语法；`nginx -t` 的弃用 warning 本身不是失败，实际校验/重载失败仍回滚。需安装带 HTTP/2 模块的 Nginx。

**只更新脚本不会自动改写现有站点。** 已有纳管站点可通过“修改”重建 HTTPS 配置，或关闭后重新启用 HTTPS（关闭期间会恢复 HTTP，请安排维护窗口）获得版本适配。重复启用只迁移统一旧式监听的显式纳管 TLS server；已有 `http2 on/off` 决策及复杂自定义配置不盲改，导入也不强制重建。修改保留已有显式 HTTP/2 决策（重建到旧版时将 `on` 转成 listen 参数、`off` 保持不启用）；复杂 include/混合监听会拒绝而非猜测。全局 `http` 上下文的自定义 HTTP/2 继承不由脚本改写。降级 Nginx 前请人工检查已有新式指令，更新脚本不会自动迁移存量配置以适配降级。

官方指令说明：<https://nginx.org/en/docs/http/ngx_http_v2_module.html#http2>（1.25.1 引入；`listen http2` 同时弃用）。

## 项目目标

通过数字菜单统一管理 Nginx，重点保证稳定性：
- 所有配置修改后都会先执行 `nginx -t`
- 校验通过才会 `reload`
- 校验或重载失败会自动回滚，避免把服务改挂

## 安装方式

### 方式一：一键安装（推荐）

```bash
bash -c "$(curl -fsSL https://raw.githubusercontent.com/Xiuyixx/Nginx-X/main/install.sh)"
```

### 方式二：手动安装

```bash
git clone https://github.com/Xiuyixx/Nginx-X.git
cd Nginx-X
bash install.sh
```

安装说明：
- 一键安装首次会克隆到 `/opt/Nginx-X`
- 再次执行会自动拉取最新代码
- 源码按 `lib/` 模块维护；安装器将全部模块打包为一个完整的 `nx` 可执行文件，更新时统一替换，模块单独变化也会被检测
- 自定义安装路径：`TARGET_BIN="$HOME/.local/bin/nx" bash install.sh --no-run`
- 配置解析和 HTTPS 开关需要 Python 3；安装（包括 `--no-run`）、主菜单启动及原“更新脚本”流程检查并补齐运行工具（普通用户需要 sudo 权限）。已有 `nft`/`ss` 时不刷新软件源或重复安装
- 如果安装目录已存在但不是 Git 仓库，安装器和更新器会停止并提示处理，不自动删除该目录
- 若安装、拉取、依赖安装或软件源刷新失败，安装器会直接提示网络/软件源相关报错，不会静默中断
- **多语言支持**：安装过程中根据系统 locale 自动切换中英文提示

> **安装完成后可直接运行：`nx`**

## 流式反代（CPA / CLIProxyAPI / SSE）

进入主菜单 **2) 配置管理** → **1) 内部反代**（同机后端端口）或
**2) 外部反代**（HTTP/HTTPS 上游 URL），填完上游后分别选择内部 **2) 流式反代** / 外部 **6) 流式反代**。
内部仅提供 1) 标准模式 / 2) 流式反代；外部原有 1–6 编号不变（2–5 为媒体方案）。内部旧输入 6 仍兼容为流式反代，但菜单不再显示；修改时回车保留当前模式。
主菜单 **5) 更新脚本、6) 卸载** 保持不变。

流式反代只在业务 `location /` 添加：

```nginx
proxy_buffering off;
proxy_cache off;
```

适用于 AI API 的增量响应与 SSE；不改变 ACME 验证 location，也不额外关闭请求缓冲、
放开请求体大小。保留 HTTP/1.1、长超时、鉴权头透传、WebSocket 与原上游路径/查询语义。
标准模式与已有 Emby/Jellyfin 模式不变；外部 HTTPS 仍沿用原有上游 TLS 设置。

**只更新脚本不会自动改变已建站点。** 旧模板站点可通过配置管理 → 3) 配置列表 →
选站点 → **3) 修改**，保留域名/端口/上游后选择 6；选 1 可切回标准模式。
再次修改时模式默认保留，切换 HTTPS、修改端口/后端或停用后修改也保留模式与启停状态。
无模式元数据的旧内部站点默认标准模式；外部继续使用原 `external_mode` 字段。
导入、手工编辑或复杂自定义配置仍按原安全限制拒绝模板重建，请用 **4) 编辑** 定点调整，
不要用模板重建覆盖自定义规则。上游本身也必须及时输出/flush；此模式不保证上游应用不缓冲。

## 当前功能

### 稳定性设计

- 所有配置变更都会先执行 `nginx -t`
- 校验或重载失败自动回滚，避免把在线 Nginx 配挂
- 443 / HTTPS 端口复用场景会优先走更安全的落地流程
- 证书申请前会做 HTTP-01 自检，并区分"软失败可继续"和"硬失败建议先修复"
- 临时文件使用安全随机文件名，降低冲突和误覆盖风险

1. **安装升级Nginx**
   - 自动检查是否已安装 Nginx
   - 未安装时自动安装依赖：`python3` `curl` `wget` `socat` `cron`
   - 自动安装 Nginx 官方 stable 版本（默认使用 nginx.org 官方源，HTTPS）
   - 安装后自动停用 `default.conf`（改名为 `default.conf.bak`）避免与自定义配置冲突
   - 自动创建证书目录：`/etc/nginx/ssl/`
   - 对比本地版本与 Nginx 官网最新版本（若 nginx.org 不可达，会回退为包管理器升级检查）
   - 有新版本时先备份 `/etc/nginx/`，再执行升级
   - 升级后自动校验并平滑重载

2. **配置管理**
   - 二级菜单包含：`内部反代` / `外部反代` / `配置列表` / `导入已有配置` / `系统DNS设置`
   - 内部反代：输入域名或本机IPv4、监听端口、后端端口，支持端口复用确认
   - 外部反代：输入域名或本机IPv4、监听端口、外部 `http/https` 上游 URL
   - 外部反代支持模式选择：
     - `标准模式`
     - `Stream 模式`
     - `Emby 分离 HTTP 推流`
     - `Emby 分离 HTTPS 推流`
     - `LilyEmby 方案（访问/推流分离，支持 sub_filter 响应体替换）`
   - Emby/Lily 模式支持配置主站上游、一个或多个推流节点 URL（多个用英文逗号分隔）、源站公开 URL、Referer URL
   - 同端口多域名场景自动适配：若目标端口已用于 HTTPS，会自动处理为可通过 `nginx -t` 的流程
   - 自动生成标准 Proxy Header，配置写入 `/etc/nginx/conf.d/域名-监听端口.conf`
   - 配置列表中的"修改"支持外部反代配置切换方案，并保留证书/HTTPS 联动逻辑
   - 修改已有配置保留 HTTPS、证书和启停状态；域名改变但缺少新证书时停止，不降级为 HTTP
   - 重复新增同域名同端口配置会拒绝覆盖，包含已经停用的配置
   - 通过"内部反代"或"外部反代"创建配置后，会自动检测证书：
     - 若已有证书：仅需确认是否启用 HTTPS
     - 若无证书：可一键"自动申请证书 + 自动启用 HTTPS（80->443）"
   - 配置列表：统一管理上述两类配置，显示域名、监听地址/端口、HTTPS、访问策略和启用状态；可直接执行 启用 / 停用 / 修改 / 编辑 / 删除 / 访问限制 / HTTPS 开关 / 健康检查
   - 导入已有配置：自动扫描 `conf.d/`、`sites-enabled/`、`sites-available/` 三个目录，发现未纳管的 Nginx 配置后逐个确认导入
   - 导入时自动提取域名、端口、后端地址、HTTPS 状态等元数据，保留原有业务指令，并按有效访问策略添加受管规则
   - 导入时保留外部原文件；仍由 `sites-enabled` 链接加载的配置会要求先手动迁移，避免事务之外删除链接或重复加载
   - 导入识别实际监听地址、端口和 HTTPS；无法安全处理的配置明确拒绝，不猜测端口
   - 已导入到 `conf.d` 的配置不会被重复扫描（按域名+端口去重，含 `.bak` 等停用文件）
   - 首次安装 Nginx 后会自动检测并提示导入已有配置
   - **仅域名访问**：在每个站点内独立开关，并管理本站默认访问入口，详细语义见下方说明。

### 域名访问限制与默认站点

所有操作统一位于 **配置管理 → 配置列表 → 选择站点 → 仅域名访问**，主菜单仅提供 **1) 开启 / 2) 关闭 / 3) 高级设置 / 0) 返回**；默认访问入口位于高级设置，不再提供独立的全局菜单。已有继承设置继续读取旧 `domain-only.conf`，保持升级前的访问行为；对本站开启或关闭后改为独立策略，不影响其他站点，也不执行状态文件中的 shell 代码。

- 严格站点仅接受 `server_name` 中的字面域名和别名。必须实际发送 Host；HTTP/1.0 缺少 Host 不会因 Nginx 的 `$host` 回退而通过。IP 和未知域名被断开（444）。
- HTTPS 还要求 SNI 与 Host 是同一个域名：主域名 SNI + 别名 Host 也会拒绝。DNS 大小写及末尾一个点会归一化；Host 可以带端口。没有 SNI 的连接不会进入严格站点。别名仍需证书覆盖，添加 `server_name` 不会自动签发包含别名的证书。
- 默认拒绝配置按实际 `地址:端口` 和地址族生成，覆盖具体 IPv4/IPv6 地址，不额外创建通配监听。共享监听上的站点分别执行自己的规则。删除/停用最后一个站点时清理对应拒绝监听。
- 显式默认站点只占有选定 socket，仍执行自身策略。**开放的默认站点故意接收 IP、未知 Host 及无 Host 请求；严格的默认站点仍拒绝它们。** 同 socket 重复默认设置会使操作失败并回滚；现有手工 `default_server` 不会被静默覆盖。
- 全局严格控制继承站点；显式开放是有意的例外。未纳管站点不会被强行改写，请先导入再设置策略。SSH、Docker 直接发布的端口及其他服务不经过 Nginx，不受 Nginx 入口规则控制；组合开启只保护核验过的本站后端端口，不泛封其他服务，也不会隐藏公网 IP。
- 严格模式保留站点的 ACME challenge location，合法域名的 HTTP-01 续期可用；生成的 HTTPS 跳转位于 `location /`，不会抢先覆盖 challenge 路径。

**仅 Nginx 入口限制不是鉴权，也不拦截后端直连；主菜单组合开启则同时保护本机后端。** 例如 CPA / CLIProxyAPI 监听 `*:8317` 时，`IP:8317/management.html` 直接到达 CPA，不经过 Nginx；即使域名站点已开启严格规则也不能阻止。客户端仍可主动发送合法 Host/SNI，敏感管理/API 入口必须保留应用鉴权。

CPA 安全部署建议：由用户自行将应用绑定 `127.0.0.1:8317`；同机 Docker 发布端口时使用 `-p 127.0.0.1:8317:8317`（容器内部可仍监听通配地址），或自行通过防火墙限制来源。调整后须保留 Nginx 到后端的连通性；Nginx 本身在容器/其他主机时不可照搬同机回环方案。**仅更新 Nginx-X 不能关闭已经暴露的 CPA 后端端口。** 脚本不会自动修改应用监听或 Docker 发布；新增的后端防护仅在用户显式选择并确认后修改项目自有防火墙规则。

### 可选后端直连保护（显式启用）

已有安装从 **5) 更新脚本** 升级即可：旧更新器拉取新的 `install.sh --no-run` 后，在替换入口前自动补工具；失败保留旧入口并提示原因。也可在原源码目录 `git pull --ff-only` 后运行 `bash install.sh --no-run`（自定义入口继续传原 `TARGET_BIN`）。`--no-run` 仅禁止进入交互菜单，不跳过依赖；source、build-bundle、`--help` 不安装包。依赖齐全不代表后端保护已开启或平台受支持。

主菜单 **1) 开启** 经一次明确确认，同时启用严格 Nginx 入口和本机后端保护；两个步骤任一失败均尝试恢复原策略、默认入口元数据、配置字节、保护引用、自有 nft 规则及注册文件，不显示完整开启。**已有 strict-only 用户升级后仍保持原状，应选择 1 补齐保护**；完整开启重复选择 1 幂等，实际规则漂移可显式修复。更新、source、健康检查不自动改防火墙。

主菜单 **2) 关闭** 先明确提示后端可能重新暴露公网，取消本站引用后解除 strict，保留其他共享站点引用；失败恢复两层设置。关闭不会自动将本站设为 IP 默认入口。主界面只显示完整开启、仅 Nginx 入口、关闭或异常，校验实际配置和 nft 状态，不将 strict-only 伪装成完整开启。

**3) 高级设置** 保留：1 仅开启 Nginx 域名限制、2 修复/启用本机后端保护、3 解除本站后端引用、4 管理默认访问入口、0 返回。外部/静态站点及不支持的后端无法组合开启，明确失败并恢复原设置；可在高级设置确认仅 Nginx 限制，不宣称后端已保护。阻止浏览器 IP 访问不等于隐藏真实源站 IP，不做 CDN 配置。

组合保护须以 root 启动脚本（例如 `sudo nx`），非 root 入口明确拒绝而不丢失 sudo 锁；strict-only 的关闭不依赖后端保护环境。首版只支持 **Linux + nftables + 运行中的 systemd**，安装器自动检测 `nft`、`ss`：apt/apk 使用 `nftables` + `iproute2`，dnf/yum 使用 `nftables` + `iproute`；只装缺失工具对应的包。最终安装维护脚本在私有 mount/network/PID namespace 中运行（软件源刷新/下载仍遵循管理员的原生包管理器 hooks），隔离 `/run`、服务管理器调用及防火墙，保留管理员 nft 配置和已有规则；缺少 namespace 权限、APT 事务涉及 init helper 变更或安装失败则明确非零拒绝，不退回普通不安全安装。包失败可能留下部分安装/待配置状态，需按包管理器报错修复后重试；不承诺包级回滚。旧 yum 必须具备 downloadonly 插件，否则明确失败。**无需启动/启用系统 `nftables.service`**（其默认配置/停止动作可能 flush 其他规则）；保护仅使用 Nginx-X 自有服务，在用户显式确认时才注册和修改规则。Alpine/OpenWrt 默认 init 不满足保护条件；不会安装/切换 systemd。OpenWrt/opkg 不猜测 nft/ss 包名、不自动安装后端工具；只有 Nginx 管理功能仍受支持。拒绝活动 UFW/firewalld/netfilter-persistent、未知或过早的 NAT 规则，不降级到仅 INPUT 或另一套 iptables。只接受活动纳管配置中所有实际代理目标均为静态 `http://127.0.0.1:端口`；外部、include、变量及复杂上游明确拒绝。核验真实 socket/进程及回环连接；22、sshd、Nginx 前端冲突、未知归属及无宿主监听（例如禁用 userland-proxy 的 Docker）拒绝，不猜测安全。

- 独立 `inet nginxx_backend_guard` 表在 DNAT 前阻断非 loopback、目的为本机的受保护 TCP 端口；覆盖 IPv4/IPv6 原生 INPUT 及常规 Docker 发布 DNAT/FORWARD 路径，不泛封路由转发同端口，不改其他表/全局 policy。
- 保留本机 Nginx 的 `127.0.0.1` 连接，不改 CPA/sshd/Docker 绑定。**所有共享该端口的其他远端使用者也会被阻断**，不是按域名识别数据包。本机用户仍可直连，合法 Host/SNI 可伪造，应用鉴权不可移除。
- 共享端口按站点引用计数：关闭 A 不解除 B 的保护。受保护站点的停用/删除/改名/编辑/后端或前端变化/关闭 strict 会被拒绝并恢复旧配置；需先显式关闭本站保护，完成修改后重新启用并验证，期间后端可能恢复公网访问。其他站点不能占用受保护后端端口。卸载有引用时拒绝，不暗中解封；取消全部引用后才允许卸载。
- 独立 root-owned `/var/lib/nginxx/backend-protection` 状态、回放程序及 `nginxx-backend-guard.service` 注册启动恢复。执行规则回放已在隔离环境实证，**实际系统重启尚未实测**；不保证外部管理器后续 flush/reload 后仍有效，需检查菜单状态。失败尝试恢复自有规则/文件，恢复失败保留备份路径；SIGKILL/掉电不保证自动事务恢复。
- 配置导入不会导入防火墙引用；导出/服务器迁移需同时安全备份上述状态/回放/unit，并重新核对 socket、网络和权限，不能复制状态就声称新机器已保护。本工具没有自动防火墙迁移接口。

CPA `*:8317` 且 Nginx 使用 `http://127.0.0.1:8317` 的原生进程符合候选范围，但仍必须通过运行时检查和显式确认；没有检查/修改用户测试服务器，不能保证其实际环境支持。测试证据包含真实私有 namespace/veth、双栈和 DNAT 模拟；**并非实际 Docker daemon 或 systemd reboot 证明**。

健康检查对可识别的内部 `http://127.0.0.1:端口` 后端，只读查看本机 TCP 监听（ss → netstat → /proc）。通配 IPv4/IPv6 或非回环绑定提示“可能绕过 Nginx”，并非保证外网可达：防火墙、NAT、容器映射及远端监听未检查。仅回环不报风险；查询失败或无监听明确说明未知/未发现，不据此保证安全。外部/复杂上游不推断暴露风险，检查不会写配置或重载。

访问策略只插入带标记的规则，HTTPS 开关保留应用 location、别名、代理目标及原有地址族，不重建自定义站点。解析无法确定的配置（例如隐藏 server 指令的 include、动态/正则域名、隐式监听、QUIC 或复杂多应用 server 文件）会明确拒绝自动修改，保留原文件；需先在编辑器中内联相关 include 或简化为可识别的 server 布局。普通“修改”仍是模板编辑器，导入或手工编辑站点需要使用“编辑”。

已有证书且复用 HTTPS 监听端口时，新站点先在临时文件生成最终 TLS 配置再发布，不先开放明文业务。无证书的申请流程仍可能先创建 HTTP 站点，请根据业务需要选择 DNS 验证或先单独申请证书。

站点内容、默认设置、全局状态及派生拒绝配置在一次事务中生成，全部校验后只执行一次重载。失败时恢复原内容和权限并尝试加载原配置；如果恢复后的服务重载仍失败会明确提示，不能把服务管理器失败当作成功。事务拒绝硬链接配置及主配置/状态文件的硬链接，以免修改快照范围外别名；已有文件的保留式改写维持所有者/权限。事务使用进程锁串行处理 nx 写操作；手动编辑及其他程序不会遵守此锁，操作时仍应避免并行修改配置目录。

### IPv6 支持说明

- **对外监听（客户端通过 IPv6 访问）**：脚本在生成配置时会进行最佳努力检测，若系统 IPv6 已启用，会额外写入：
  - `listen [::]:80;`
  - `listen [::]:443 ssl;`（或对应的 HTTPS 监听端口）
- **上游反代到 IPv6**：支持上游 URL 使用 IPv6（需要按 URL 规范使用方括号），例如：
  - `http://[2001:db8::1]:8080`
  - `https://[2400:3200::1]`

> 注意：若你的系统内核禁用了 IPv6（例如 `net.ipv6.conf.all.disable_ipv6=1`），脚本会自动跳过 IPv6 的 `listen` 行，避免 `nginx -t` 失败。

   - 自动续期每日检查，证书部署注册持久重载钩子；先校验 Nginx 配置再重载，失败明确报告

## 系统兼容性

- 提供 Ubuntu / Debian / CentOS / Alpine / OpenWrt 的包管理器适配；各发行版版本、服务管理器和预装组件可能不同
- 包管理器自动检测（apt / yum / dnf / apk / opkg）
- 脚本需要 Bash；部分操作另需 Python 3、OpenSSL 及标准文件工具。Alpine CI 安装这些运行依赖，不能据此推断所有精简 BusyBox 镜像都具备相同环境。
- Nginx 安装后自动适配配置目录：Alpine 使用 `http.d`，其他系统使用 `conf.d`

共享访问策略保存于 Nginx 配置目录中的 `.nx-access-state`，不随管理用户的 HOME 改变。邮箱、DNS API 等个人凭据仍保留在用户配置目录。旧策略迁移优先保留已有严格规则，避免切换管理员导致站点开放。

## 已知限制

- HTTP-01 自检在 CDN、四层转发、NAT 回环等特殊网络环境下可能出现误判，可切换 DNS-01 方式规避
- 站点流量基于 Host 专用日志最近5000条记录；未配置日志时显示无法统计。网卡流量属于整个系统，不等于 Nginx 独占流量

## 交互与失败处理说明

- 菜单类入口在缺少前置条件时，会提示原因并返回上一级，不会因为 `set -e` 直接退出整个脚本。
- 安装 / 升级链路里若遇到网络不通、GitHub 不可达、软件源异常、签名密钥下载失败等情况，会给出更明确的错误提示。
- 证书邮箱配置保存在用户配置目录，而不是脚本安装目录，避免因 `/usr/local/bin` 不可写导致保存失败。

## 建议的 Host 专用日志格式

如果你希望"流量统计"更准确，可在 Nginx 主配置里增加类似：

```nginx
log_format nginxx_host '$host $body_bytes_sent $remote_addr [$time_local] '
                      '"$request" $status $http_referer "$http_user_agent"';
access_log /var/log/nginx/access.host.log nginxx_host;
```

这样脚本会优先读取 `access.host.log`，按域名做更准确的请求数和下行统计。

## 备份与恢复边界

- 配置事务快照用于当前操作失败时恢复配置、权限和访问策略，不是长期保存的灾备副本；恢复失败时会提示保留的备份路径，应及时人工处理。
- Nginx 升级前的 `/etc/nginx/` 备份与系统 DNS 修改前的备份各有独立范围，不能代替 ACME 账户、证书私钥、邮箱/API 凭据以及续期调度的完整备份。
- 配置导入只负责纳管支持的站点配置，不会自动迁移账户、凭据、证书及任务。本项目目前不提供完整的导出迁移包或一键灾难恢复向导。
- 迁移服务器前，请另行安全备份配置、证书及 ACME 账户、个人状态和调度，保留所有者及权限；私钥与 API 凭据不得公开发布，并应在隔离环境验证恢复。
- 联合恢复清单：主配置/站点/共享访问策略、SSL key/chain、各账户 ACME home（含部署 stage）、邮箱/API 状态、受保护的 `acme-*.domains` manifest 与 dispatcher、root 及账户 crontab、账户所属 periodic 任务。恢复到原身份与受信路径后，先校验权限和证书域名，再 `nginx -t`，验证实际 TLS/HTTP-01 请求，最后恢复原调度；明确关闭的账户不要自动开启。恢复凭据应通过安全通道，禁止把含私钥的归档放入仓库。
- 新增隔离联合备份回放检查字节/权限及恢复 dispatcher；不是产品一键恢复接口，也不保证 SIGKILL/掉电时可自动恢复。续期开关影响当前 ACME 账户全部证书；调度迁移多步失败会返回失败并保留安全、可重试的部分完成状态，不宣称整个系统 cron 事务回滚。
- Nginx 安装后的默认配置调整单独快照，应用失败恢复其文件/权限并尝试重载；软件包安装、仓库设置及服务启用不能整体撤销。已有 `default.conf.bak` 时拒绝覆盖。系统 DNS 发布采用非目录 rename（GNU/BusyBox `mv -T`），渲染/发布失败不替换原文件或链接。

### 自更新交接与信号边界

主菜单 **5) 更新脚本** 有实际产物变化且安装成功后，会自动 `exec` 新版，
无需按 Enter。新版继续使用原前台进程组和终端，可正常输入；普通菜单的
Ctrl+C 行为恢复。失败或内容无变化不启动新版。

更新助手由脚本临时生成，不依赖 systemd/额外服务。权限确认后启动独立
session 的助手，标准输入为 `/dev/null`，输出写入私有日志，管道握手确认
启动与完成。更新关键期忽略 INT/HUP，在线前台监督完成并自动交接；SSH/PTY
关闭后助手仍可发布，**不会尝试在没有终端的后台运行菜单**。重新登录运行
`nx` 即加载已发布版本。关闭终端之前若尚未显示“更新助手已启动”，交接
尚未得到确认。TERM、SIGKILL、机器断电或登录会话被系统强制整体清理不保证
完成；没有永久禁用 Ctrl+C 或无限抗 TERM。

每次任务打印 `/tmp/nginxx-update-*` 日志/状态目录（0700，文件0600）；使用
sudo 更新时需 `sudo cat <目录>/log` / `sudo cat <目录>/status` 查看。状态0为
已发布、10为无变化、其他非零为失败。保留日志以便恢复，可事后手动删除。
仓库和入口的相邻 `.update.lock` 为私有常规文件，防重复更新，交接前释放，
不要在运行中删除。沿用安装器的依赖检查与原子替换，缺失依赖可能由安装器
安装；不会注册后台服务。exec 失败返回非零并提示手动启动入口和日志位置。
